# 装備実現可能性モデル基盤 設計

更新: 2026-11-04

## 意図

Phase 3 の最初の単位として、正規化済み MHDB データを型付きの装備候補へ読み込み、防具5部位・通常護石・防具用装飾品の組合せがスロットと要求スキルを満たすかを Python-MIP と HiGHS で判定できるようにする。火力目的関数を急いで混ぜず、後続の候補生成とダメージ再評価が依存できる、検証可能な実現可能性モデルを先に確立する。

## ゴール

- 正規化済み `skills.json`、`armor.json`、`decorations.json`、`regular_charms.json` を不変の Python モデルへ読み込む。
- 頭・胴・腕・腰・脚から各1件、通常護石から1件を選択する。
- 選択した防具と護石が持つ各スロットへ、適合する防具用装飾品を0個または1個配置する。
- 武器用装飾品を防具スロットへ配置できないようにする。
- スキル要求 `minimum`、`exact`、`forbidden` を相互に矛盾しない形で表現する。
- 小さな人工データについて、Python-MIP の実現可能解集合が独立した全探索の結果と一致することをテストする。
- 不正な入力、解なし、ソルバー異常を区別して返す。

## 非ゴール

- 火力代理目的、Top N、ダメージ再評価。
- 武器選択と武器スロット。
- シリーズスキル、グループスキル、発動条件付きスキル効果。
- 巨戟アーティア、鑑定護石、所持装備制限。
- 正規化データのGit管理や再配布。
- CLI設定ファイルと最終レポート。

これらは、今回の実現可能性モデルを小さなテストで固定した後に追加する。

## 検討した方式

### 1. 人工データ専用の制約モデルから始める

最短で Python-MIP を試せる一方、実データ接続時にID、スロット、スキル上限の扱いを作り直す可能性が高い。

### 2. データ読込・型定義と最小制約モデルをまとめて作る（採用）

ユーザーが選択した方式。正規化スキーマを境界にし、実データと同じ型を人工データのテストでも使う。実装量を抑えながら、後続機能が流用できる基盤になる。

### 3. 候補生成、火力再評価、Top Nまで一括実装する

早く結果表示まで到達できるが、データ不正、制約誤り、評価誤りを切り分けにくい。Phase 3 の最初の単位としては範囲が広すぎる。

## モジュール構成

### `mhwilds_optimizer/equipment_models.py`

不変の dataclass と列挙型を置く。

- `SkillDefinition`: ID、種別、最大レベル。
- `ArmorPiece`: ID、部位、スキル、スロット。
- `Decoration`: ID、スロット種別、必要レベル、スキル。
- `RegularCharm`: ID、スキル、スロット。
- `EquipmentCatalog`: 上記候補とスキル定義。
- `SkillRequirement`: `minimum | exact | forbidden` と必要レベル。
- `DecorationPlacement`: 装備ID、スロット位置、装飾品ID。
- `FeasibleBuild`: 防具5部位、護石、装飾品配置、合計スキル。

ID比較は表示名でなく正規化済みIDを使う。コレクションは呼出し側から変更できない形に変換し、同一ID、未知スキル、範囲外レベル、未知部位、無効なスロットを境界で拒否する。

### `mhwilds_optimizer/equipment_data.py`

正規化ディレクトリを読み、4ファイルを `EquipmentCatalog` へ変換する。JSON構造、外部キー、件数の整合を確認し、`manifest.json` の対象ファイル一覧と件数にも一致させる。正規化処理が保証していることを暗黙に信用せず、手編集や破損を明確な読込エラーとして扱う。

### `mhwilds_optimizer/constraints.py`

Python-MIP のモデル生成と HiGHS による求解、解の復元を担当する。

- 防具選択変数 `x[a]` は二値で、部位ごとの合計を1にする。
- 護石選択変数 `z[c]` は二値で、合計を1にする。
- 装飾品配置変数 `y[owner, slot, decoration]` は二値とする。
- 各スロットの配置数は、そのスロットを持つ装備の選択変数以下にする。
- `required_slot_level <= slot_level` かつ `slot_type == armor` の候補だけに配置変数を作る。
- スキル総量は、選択装備の付与量と配置装飾品の付与量の線形式とする。

装飾品を個数変数だけで表す方式は採用しない。明示的なスロット割当てにより、合法性と出力配置を同じ変数から復元し、後で武器スロットを追加しても種別を混同しないようにする。

## スキル要求の意味

- `minimum: L`: 付与レベル合計が `L` 以上。
- `forbidden`: 付与レベル合計が0。
- `exact: L`: `L` が最大レベル未満なら付与レベル合計がちょうど `L`。`L` が最大レベルなら、上限超過分がゲーム上切り捨てられるため合計が `L` 以上。

`minimum` と `exact` の要求レベルは1以上かつスキル最大レベル以下に限定し、`forbidden` はレベルを持たない。同じスキルへの複数方式の指定や `minimum: 0`、`exact: 0` のように意味のない指定は受け付けず、設定境界で一意な要求へ正規化する。

要求されていないスキルは上限超過を許すが、`FeasibleBuild` の有効レベル表示では最大レベルに切り詰める。付与合計も診断用に保持し、制約で使った値を追跡できるようにする。

## 解の列挙とステータス

公開APIは、まず1件を解く関数と、テスト・小規模用途向けに全件を列挙する関数を分ける。

- `solve_feasible_build(...)`: 最初の実現可能解とステータスを返す。
- `enumerate_feasible_builds(..., limit=None)`: 解を復元するたびに二値変数へ no-good cut を追加し、異なる完全構成を列挙する。

ステータスは少なくとも `feasible`、`infeasible`、`error` を区別する。今回目的関数を持たないため `optimal` や `heuristic` は表示しない。列挙順には意味を持たせず、テストでは構成シグネチャの集合を比較する。

## 全探索オラクル

テスト内にソルバー実装と独立した小規模全探索を置く。各部位、護石、各スロットの「空または適合装飾品」を直積で列挙し、純Pythonで要求を判定する。製品コードと式を共有しすぎず、同じ誤りを複製しないようにする。

比較対象は次を含む。

- 部位ごとに1件だけ選ばれる。
- 小さい装飾品は大きいスロットへ入る。
- 大きい装飾品は小さいスロットへ入らない。
- 武器用装飾品は候補にならない。
- 装備、護石、装飾品のスキルが合算される。
- `minimum`、最大未満/最大ちょうどの `exact`、`forbidden`。
- 実現可能解なし。

## 依存関係と失敗方針

プロジェクトの Python 要件を `>=3.11,<3.12` に変更する。Apple Silicon では PyPI の安定版 `mip==1.15.0` に同梱されたIntel向けCBCを使用できず、HomebrewのCBCもPython-MIP 1.15.0固有のC APIと互換性がない。そのため、Python 3.11に対応したPython-MIP公式リポジトリのコミット `50f00c92b3b093d7bd554a61e5e672e5c5e43aec` を固定し、`highs` extraを有効にしてHiGHSを初期ソルバーにする。この組合せは対象のApple Silicon環境で二値モデルの求解まで確認済みである。ソルバーを初期化できない環境では、空結果や `infeasible` に偽装せず、原因を含む `error` ステータスを返す。

ローカルの正規化データが存在しなくても人工データの単体テストは実行可能にする。実データ接続テストはダウンロード済みデータがある場合だけ追加検証として実行し、通常のテスト成功条件にはしない。

## 後続への接続

次の作業単位で、シリーズ/グループスキルと武器スロットを実現可能性モデルへ追加する。その後、複数の線形代理目的で候補集合を作り、既存の `calculate_combo_damage` で再評価して Top N を出力する。近似候補の最高値は `heuristic` と表示し、今回の実現可能性判定と火力最適性を混同しない。
